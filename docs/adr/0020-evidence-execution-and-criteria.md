# 0020 — Evidence execution, exact binding and criteria status

Status: accepted (M3.1-M3.5; final at M3.7). Builds on ADR 0012 (pinned evidence and selection) and ADR 0008 (root-authenticated sessions).

## M3.1: definitions and exact binding

Check definitions are validated by `evidence.ValidateDefinition` when `intent.create` pins them. Rules beyond the record schema: names match the record name pattern; the working directory is a clean, NFC, repository-relative path (no absolute path, `..`, `.`/empty segment, backslash or NUL); commands and setup are non-blank without NUL; allowlisted variable names are valid and unique; timeout is 1..86400 s; `output_limit_bytes` is at most `MaxOutputLimit` (64 MiB). The schema permits 1 GiB, so the stricter cap is a run-time safety limit and a definition above it is rejected at pinning with `invalid_checks`. Only definitions a criterion references are validated, so an unused broken entry in `checks.json` does not block an unrelated intent. Judgment-category definitions can be pinned but are never runnable (`evidence.Runnable`); M3.3 enforces that when a run is requested.

A binding is the triple manifest id, bound commit SHA and definition hash(es). `evidence.resolve` is read-only and accepts either `{change_id}` or `{manifest, commit?}`. A change id resolves once, to the workspace's current proposal, and the response (`frozen: true`) carries the manifest, commit, tree, base commit, intent, workspace, author session and each pinned definition with the criteria it serves. Callers use those values from then on. A later rework creates a new manifest; the earlier manifest still resolves to its original commit and definitions. A supplied commit that differs from the commit bound to the manifest fails with `binding_mismatch`. The pinned definition is read from the stored `check_definition` record, so later edits to `.ledger/checks.json` cannot change it.

`verify.CheckBinding` reports the trailer, tree and parent conditions separately as `ok`, `mismatch` or `unavailable` (AC-057). The trailer is the last paragraph of the commit message, parsed literally, with exactly one `Ledger-Manifest:` line naming the manifest.

Deviations and ambiguities:
- The parent condition requires exactly one parent equal to the manifest base commit, not merely a first parent equal to it. ADR 0010 makes every proposal a sole-parent replacement commit, so a merge-shaped commit is not a Ledger proposal.
- `evidence.Resolve` takes no `*gitx.Repo`. Resolution reads only the index; the commit object is first read by the verification worktree (M3.2), where an absent object is `dependency_unavailable`.
- `index.Proposal` gains the proposal receipt's `manifest`, so a change id resolves without a second lookup.

## M3.2 verification worktrees

- `evidence.Prepare` creates a detached worktree at `.ledger/runtime/verify/<run-id>/`, after reading the bound commit and checking trailer, tree and parent (`verify.CheckBinding`). Nothing is created if any condition fails. After checkout it compares `HEAD^{tree}` and a tracked-files tree (temporary index, `read-tree` + `add -u` + `write-tree`) with the manifest tree. Untracked and ignored files are allowed; modified, deleted and mode/type-changed tracked files are not.
- Deviation from the plan text: a binding failure is `binding_mismatch` except when only the tree condition fails, which is `tree_mismatch` (AC-091 names tree mismatch as its own abort). All three conditions are always in the error details. Dirty tracked files are `dirty_checkout`.
- Run journals (`.ledger/runtime/evidence/<run-id>.json`, runtime schema `evidence_run`) move `preparing -> ready`, or `aborted` with the error code. `Reconcile` (called from `core.New`) marks non-terminal journals `interrupted` and removes the worktree only if its journalled path is exactly the run's verify path and git lists it as a detached worktree; other paths are never touched. `system.status` reports `interrupted_runs`. A fault hook error simulates a crash and skips cleanup.
- Worktree removal on abort uses `context.WithoutCancel`, so a cancelled request still cleans up.

## M3.3 evidence run
- `evidence.run` has three phases. Under the service lock it replays a committed operation, checks the run journal for the operation id, resolves the binding, provisions the verifier and writes the journal. It then runs `evidence.Execute` unlocked, so other requests proceed while a check runs. Under the lock again it signs and publishes with the original operation id, request digest and the verifier as signer. `(*Service).publish` is `mutate`'s locked `DoEffects` call plus dropping the keys of sessions that ended.
- Deviation from the plan text: the verifier capability is `allow: ["**"], deny: ["**"]`, not `allow: []`. The capability schema requires a non-empty allow list and deny wins, so the session has no path authority. The verifier session is created by an operation named `evidence.verifier` rather than by dispatching `session.create`, reusing `newSession` and the same root-signed records.
- The session is ended with a root `session.end` after publication or after a refused checkout. A run that crashes leaves its session active until startup reconciliation ends it (its key is lost), exactly like any other lost session.
- Journal states: `preparing`, `ready`, `running`, then `published`, `interrupted` or `aborted`. `Prepare` or `Execute` failures that are not simulated crashes end `aborted`. A publication error marks the run `interrupted` (`publication_failed`); because the record store may still complete the journaled group on restart, `core.New` settles any `interrupted` journal whose operation id is committed to `published`, and `system.status` omits such runs. A retry replays a committed result before it looks at the journal, so a recovered attestation is never reported as interrupted.
- A lost verifier key is detected at signing time: the journal becomes `interrupted` (`verifier_key_lost`) and `run_interrupted` is returned with the run id and frozen binding. Retrying the same operation id returns the same error; a new id starts a fresh run.
- Execution details: each phase runs under `/bin/sh -c` in its own process group with no stdin; stdout and stderr share one pipe copied into `BoundedOutput`; the group is killed on timeout, on cancellation and after the shell exits. A process that leaves the group (for example with `setsid`) is not tracked. Phase 2 uses `context.WithoutCancel` for tracked-content checks and worktree removal, and publication uses it too, so a cancelled client still produces a failed `cancelled` attestation (the daemon's request context is cancelled when the client disconnects; `daemon.TestAC111_CancelledRunRecordedWhenClientDisconnects`).
- An exit killed by a signal that Ledger did not send, a timeout and a cancellation record `exit_status: null`. A working directory missing from the checkout, or a symlink leaving it, aborts the run with `invalid_working_directory` and no attestation (a definition fault, not a check result).
- The environment (OS, architecture, toolchain versions, variable digests, lockfile hashes) is described after setup, so dependencies and lockfiles that setup produced are included. Toolchains are probed with the reduced environment through the same shell, so `PATH` must be allowlisted for a check to see tools outside the shell's default path.
- Publication validation (`checkAttestation`): verifier is an active session that is not the manifest author and was never bound to its workspace; the commit equals the manifest's receipted commit; the executed tree equals the manifest tree; the definition is a stored `check_definition` of the same category; every criterion exists and (for mechanical and behavioral) is pinned to that definition; `pass` carries no reason and clean phases, `fail` carries a reason. Judgment attestations are validated for criterion kind only until M3.4.
- The CLI sends `evidence.run` without the 5-minute deadline other live commands use; interrupting the CLI disconnects and cancels the run.
## M3.4 independence and criteria status
- The evaluator lives in the pure package `internal/selection`, so the index, core and later bundle verification share one definition of applicable evidence. An attestation decides a criterion only if it names the exact manifest, commit and tree, lists the criterion, has the right category (mechanical or behavioral for a check criterion, judgment for a judgment criterion), matches the pinned definition hash for check criteria, has an independent signer, satisfies the reviewer kind for judgments, is consistent (a `pass` has clean phases and no reason), and has `isolation: "none"`. Anything else is listed in `rejected` with a reason and never deleted.
- Independence is re-derived by every reader from indexed records: the signer is the attested verifier session, a session whose creation was signed by a root key, not the manifest author and never bound to the manifest's workspace. Publication refuses author and holder signers (`author_signed_evidence`); the reader flags them anyway because a fetched group is not publish-validated. Independence says nothing about correctness and `evidence.isIndependent` returns a note saying so.
- Status per criterion: no applicable attestation is `outstanding`; any applicable failure is `failed` with the failing hashes in `deciding` and the passing hashes in `conflicting` (non-empty `conflicting` is the mixed-result conflict detail); otherwise `satisfied` with the passing hashes in `deciding`. `contrary_evidence` is every known applicable failing attestation for the binding, whether or not it was in the evaluated set. Evidence for another revision is an error (`cross_revision_evidence`) when named, and absent from the default set.
- `evidence.judge` takes `{manifest, commit, criterion_id, result, reason?}` and has no reviewer member. The reviewer kind is the `participant_kind` of the signing session, which only root can set. A root caller gets a fresh `human` verifier session (created, used and ended inside the call, like M3.3); a session caller signs as itself and must not be the author or a workspace holder. A service session may record a judgment, but it never satisfies one. Only the current proposal of the workspace can be judged (`stale_revision`), and only judgment criteria (`not_judgment`).
- Deviation from the plan text: the judgment definition record is named `judgment`, not `judgment:<criterion>`. The check-definition name pattern forbids `:` and a prefixed 64-character criterion id would exceed the 64-character limit. The criterion is carried by the attestation's `criteria`, which publication requires to hold exactly one id, no process phases, and a definition named `judgment`.
- Deviation from the plan text: the mixed-result conflict detail is the non-empty `conflicting` list of the closed `criterion status` object (the same shape a selection decision records), not an extra boolean member.
- `evidence.isIndependent` and `intent.criteriaStatus` are read operations; `evidence.judge` is a mutation that, like `evidence.run`, publishes under the caller's operation id so a retry replays the frozen result even without keys.
## M3.5 selection decisions
- `selection.record` takes `{manifest, commit, evidence, competitors?, scoring?}` and nothing else. There is no member for criteria, statuses, outstanding lists, contrary evidence or selector, so a fabricated status fails schema validation. `selection.Build` recomputes every status with `selection.Evaluate`, lists `contrary_evidence` from all known evidence for the binding (relied on or not), and sorts and de-duplicates `evidence` and `competitors`. `outstanding` in the result is derived from the recorded statuses; `accepted` is the literal `false`.
- The caller is root or an active session that is not the manifest author. The selector is the signer (`root` with its fingerprint, or `session` with its id); `speculation_run` selectors stay unused until M5.4. The manifest must be the workspace's current proposal of a `proposed` workspace (`stale_revision`, `invalid_state` otherwise) and its intent must be open. Named evidence that is unknown is `unknown_evidence`; evidence for another manifest, commit or tree is `cross_revision_evidence`. Competitors must be other committed manifests of the same intent (`invalid_competitor`).
- The index validator re-derives everything at publish (`checkSelection`), so a decision built outside the API is held to the same rules: the selector equals the signer, the signer is not the author, the manifest is the current proposal, the commit is the receipted one, evidence is committed and exact-revision, and the recorded criteria and contrary evidence equal a fresh evaluation (`status_mismatch`). Evidence cannot be published in the same group as the decision.
- Deviation from the plan text (decision 10, restated): a selection does not move the workspace to `selected`. `lifecycle` makes `selected` terminal with no cleanup path, and the single atomic winner/loser resolution group is M5.4. AC-051 therefore stays partial until M5.4. Selecting again (for example after new evidence) is allowed; each decision is an immutable record and none supersedes another.
- Selection is not acceptance. It writes one signed record. It changes no branch, tag, proposal ref or `HEAD`, creates no commit, invokes no merge, and leaves the intent and workspace states unchanged (`core.TestAC060_232_247_SelectionIsNotAcceptance`). An unreviewed judgment is recorded as `outstanding`.
- Deviation from the plan text: competitors reject the selected manifest itself, and `evidence` is a required member (an empty list is a valid, fully outstanding selection) so omission is not mistaken for "all known evidence".
- `Index.SelectionsFor` and an `objects_selection_manifest` index support lookup by manifest.
## Decisions for M3.3-M3.5 (recorded now so later steps cannot drift)

1. Verifier sessions are provisioned per run by the daemon: an ephemeral root-signed `service` session with no path authority, ended after the run, so the signer is never the author.
2. `evidence.run` does not hold the service lock while the child runs: resolve and journal under the lock, execute unlocked, publish under the lock using the original operation id so a retry replays the frozen result.
3. A run journal under `.ledger/runtime/evidence/` is reconciled at startup; an unfinished run becomes `interrupted` and is reported, never turned into an attestation.
4. Judgment attestations bind the criterion and revision rather than a pinned definition. The reviewer kind comes from the authenticated signing session, never from a caller-supplied label.
5. The output digest covers the first `output_limit_bytes` of combined stdout/stderr; the total size and a truncation flag are recorded.
6. The child environment contains only allowlisted variables; the attestation stores digests of their values, never the values.
7. A `pass` is applicable only if setup (when present) and check both exited 0 without timing out.
8. Independence: the signer is not the manifest author and not any session ever bound to the manifest's workspace.
9. Criterion status over an explicit evidence set: no applicable evidence is outstanding, any applicable failure is failed (passing results listed as conflicting), otherwise satisfied. Known contrary evidence is always returned.
10. `selection.record` does not move a workspace to `selected`: that terminal transition belongs to M5.4's single resolution group, so AC-051 stays partial until then.
